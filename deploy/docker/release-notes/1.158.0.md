## 1.158.0 (2026-10-20)

### ⚠ BREAKING CHANGES

* **group policy:** registry values set by Group Policy are applied only by the next Windows agent release, which is not out yet. Until then the resultant set of policy shows such PCs as not supporting them. Agent settings and scripts in a policy work with every agent now. Deploy this hub before that agent, as always

### Features

* **permissions:** permission groups now nest, the way Active Directory groups do. Give a group a **Parent group**, or open a group and press **New subgroup**. The page shows the group tree on the left and the selected group with its subgroups on the right. A member of a subgroup gets everything every group above it grants, capabilities and machines both. A subgroup can only add to its parents, never take anything away. Inherited capabilities show as dashed badges, and as ticked, locked boxes in the editor naming the group they come from. Existing groups stay at the top level, so nobody's access changes until you nest something
* **pc tree:** a new **PC tree** page (Operate) shows the fleet the way Active Directory Users and Computers shows a domain: your AD OUs (read-only, from the last directory sync) beside the hub's own nested **folders** for what AD does not cover. File PCs by ticking them and choosing **Move selected to…**, or by dragging them onto a folder. A PC is in at most one folder
* **permissions:** a permission group can be scoped to **machines in a PC folder**. It covers every PC filed in the folder or in any folder beneath it, and follows the tree at once
* **rules, watchdogs, device groups:** a new **PC folder** target, with *and sub-folders*
* **group policy:** a new **Group Policy** page (Operate), modelled on Windows' Group Policy Management. Write a policy once and link it to every PC, an AD OU or a hub folder. A policy can override agent settings (report and sensor intervals, network collection, the ticket tray), set registry values under `HKLM\SOFTWARE\Policies`, and run a library script once on each PC. The node nearest the PC wins, link order 1 wins within a node, **Enforced** links cannot be overridden from below, and **Block inheritance** stops policies from above. **Resultant set of policy** shows, for one PC, which policy won each setting and what the PC reported. See `docs/group-policy.md`

### Security

* a new capability, **Manage PC tree**, is needed to create folders and file PCs. Because a folder can be a permission scope, filing a PC is a grant: you can only file PCs already in your own scope, and only move a folder when every PC beneath it is in your scope. Browsing the tree needs only **View**, and shows only your own PCs and the OUs they are in
* a new capability, **Manage Group Policy**, is needed to write policies; a policy that runs a script also needs **Issue commands**. Every PC a change can reach must be in your own scope, and a link keeps applying only to the PCs its author could reach
* Group Policy never writes outside `HKLM\SOFTWARE\Policies`, never touches Windows Update policy, and never overwrites a value it did not write: a value set by a domain GPO, Intune or a person is left alone and shown as **Managed elsewhere**
* an invite link into a subgroup is checked against what joining it really grants, parent groups included
* a group with subgroups, and a folder that still holds PCs or that a rule, watchdog, device group, folder-scoped permission group or policy link still names, cannot be deleted. Nor can a library script a policy runs. The refusal names what is in the way

### Bug Fixes

* **rules:** the **AD organisational unit** target matches OUs component by component, as permission scope always has. `OU=Cajas` no longer also reaches PCs in `OU=NoCajas`. Check any rule aimed at an OU whose name is the tail of another OU's name: it now reaches fewer PCs
