## 1.143.0 (2026-10-09)

### Features

* **docker:** ship the hub as a container image, `ghcr.io/aw08-2004/temp_monitor-hub`, on Docker Engine or Docker Desktop, with `deploy/docker/compose.yaml`. All state is one volume (`/state`: `.env`, `logs/`, `data/`), the image runs as a non-root user, and the port is published on loopback only (#118) (774c98e)
* **docker:** a container hub never updates itself. `HUB_UPDATE_MODE=image` (set by the Dockerfile) switches off the update watcher, **Update now**, the boot-time self-heal and `hub.auto_update`, because an in-place update would vanish on the next recreate and leave the hub quietly back on an older version. The sidebar still announces a new version and says to pull the image (#118) (774c98e)
* **docker:** publish a tag for every hub version, `X.Y.Z` and `latest` from `main`, `beta-X.Y.Z` and `beta` from `beta`. The workflow refuses a malformed `HUB_VERSION` or a tag that already exists, and only runs for pushes that touch `hub/` (#118) (774c98e) (11c1b51)
* **docker:** install the image's dependencies from `hub/requirements.lock`, exact versions with every wheel hash-checked, generated by `python tools/lock_hub_requirements.py`; the hub test suite fails when the lock stops covering `requirements.txt`. The Windows service keeps using the unpinned `requirements.txt` (#118) (30d08d5) (bb0e7cb)

### Bug Fixes

* **recordings:** keep the PC's own reason when a recording's badge fails, show it after the message, and write it to the `recording_end` audit entry, so a failure like "could not attach to the input desktop" is diagnosable from the console instead of from the database (#118) (d84f070)

### Documentation

* A hub installed as the Windows service is unchanged by this version: `HUB_UPDATE_MODE` defaults to `self`. Moving an existing hub into Docker is a manual cutover, described in the README under *Running the hub in Docker*. The image package is public, so a hub host pulls it without `docker login`.
