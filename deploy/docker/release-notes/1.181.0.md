## 1.181.0 (2026-11-17)

### Features

* **sign-in:** sign in with an Active Directory account. For a domain with no ADFS and no Entra ID, the sign-in page can show a user name and password form that the hub checks against a domain controller over LDAPS. Only members of one login group, nested groups included, can sign in this way. Set it up at Settings → Sign-in, or with the `LDAP_*` keys in `.env`; docs/access.md walks through letting one group in. What a member can do still comes from `ALLOWED_EMAILS` and the permission groups, which can map the group by its distinguished name. Where ADFS or Entra ID exists, keep using OIDC: it brings MFA and the hub never sees a password
* **sign-in:** the sign-in page cannot lock out a domain account. Before it tries a password, the hub reads the domain's lockout threshold and the account's own count of wrong passwords, and refuses rather than send the one that would lock it. Wrong passwords typed elsewhere count too. If that count cannot be read, the hub stops after 4 wrong passwords for an account until 70 minutes have passed. Every refusal shows the same message; the hub log records the real reason
* **sign-in:** Active Directory settings written into `.env` by hand get the same checks as Settings → Sign-in. A plain `ldap://` server without `LDAP_ALLOW_INSECURE`, a group name instead of its distinguished name, or a missing CA file switches this sign-in off, and the hub log says why at startup
* **settings:** a sign-in secret that `.env` cannot store as typed, such as a password with a space followed by `#`, is now written in quotes and reads back exactly as it was entered

### Bug Fixes

* **docker:** a new Docker volume no longer leaves you in a restart loop with no documented way out. The example `.env` keeps the sign-in keys out of the host file, but the hub will not start without one, and Settings → Sign-in cannot be reached until it does. docs/installation.md now shows the one command that writes the first provider into the volume, and the startup error points there
