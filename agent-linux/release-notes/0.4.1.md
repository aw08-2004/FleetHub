Linux machines now follow the release channel the console sets, and they say so in the journal when an update cannot be fetched.

**Deploy the hub first.** Use hub 1.184.0 or later. Any hub that offers release channels already sends a Linux machine its channel. 1.184.0 is only the matching release.

## Beta now means beta on Linux

Until this release, the Linux agent ignored the release channel. A Linux machine set to **beta** in the console kept reading the stable manifest, so it never received a beta build. The console still showed it as beta, and nothing anywhere said why it was not updating.

From 0.4.1, a Linux machine reads its channel from every heartbeat, as a Windows PC does:

- **On beta**, it installs the newest beta build. While stable has something newer than the newest beta, it installs that.
- **On stable**, it installs only stable builds.
- **A version pin** in **Settings → Fleet** still beats both.
- **The channel is remembered across restarts**, so a beta machine's first check after a reboot already looks at the beta build.

**A machine on 0.3.0 cannot learn this by updating itself.** 0.3.0 reads only the stable manifest, so a 0.3.0 machine on beta reaches 0.4.1 in one of two ways:

- **On its own** once 0.4.x is promoted to stable.
- **Today**, by pointing it at the beta build once. As root on the machine:

  ```bash
  echo 'FLEETHUB_UPDATE_MANIFEST_URL=https://raw.githubusercontent.com/aw08-2004/FleetHub/main/agent-linux/agent-linux.manifest.beta.json' >> /etc/fleethub/agent.env
  systemctl restart fleethub-agent
  ```

  Within about fifteen minutes the machine moves to the newest beta. When it reads 0.4.1, remove that line from `/etc/fleethub/agent.env` and restart the service again. From then on the console's channel setting takes over.

## Update problems show up in the journal

- **A failed update check is now a warning** in `journalctl -u fleethub-agent`, and it names the reason: the manifest could not be reached, a signature did not match, or the download timed out. It used to be hidden below the journal's level, so a machine that could not look for updates looked the same as one with nothing to install. A failure is logged once, and again only if it changes.
- **Slow links can download the update.** The agent is about 70 MB. The download used to share the manifest's 30-second limit, so a slow connection cancelled it at every attempt. It now has fifteen minutes.
- **A failed update is retried the next day.** After three failed restarts onto the same version, the agent stops trying that version, as before. Previously it stopped for good, even when the cause was temporary (a full disk, the hub unreachable at the wrong moment). It now tries again after 24 hours. Machines stuck behind the old rule try again on their first check after updating.

## If it misbehaves

- **Check the version.** The machine page should read 0.4.1.
- **Read the log.** Run `journalctl -u fleethub-agent | grep update`. A machine that changes channel logs *Release channel is now beta* and the address it will use.
- **The machine stays on an old version.** Check `/etc/fleethub/agent.env` for `FLEETHUB_NO_UPDATE=1`, or for a leftover `FLEETHUB_UPDATE_MANIFEST_URL` line. Either one overrides the console.
